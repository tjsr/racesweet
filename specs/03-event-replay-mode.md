# Event replay SSE and control foundation

**Status:** Implemented. This specification records the delivered replay
foundation. The final protocol, seeking, and subscriber experience are tracked
in [08-event-replay-protocol-and-seeking.md](08-event-replay-protocol-and-seeking.md).

## Purpose and acceptance criteria

Let authenticated clients stream recorded event/session data at scaled recorded
intervals or receive newly accepted live records. Operators with `race:write`
can control a named replay through HTTP. A later subscriber to the same replay
receives the records already emitted and its current state.

Acceptance for this foundation requires working SSE and HTTP endpoints,
selection and authorization checks, ordered timed replay, live filtering,
start/pause/resume/reset/speed controls, a late-subscriber snapshot, completion,
and timer/subscriber cleanup. It does not imply the final public event contract,
seek support, or a full in-app replay viewer.

## Preconditions and integration points

- Session race-state records come from `EventCatalogService` and remain
  read-only during replay.
- The application server has authenticated `race:read` and `race:write`
  permissions and can publish newly accepted records to `EventReplayHub`.
- Reports owns event/session selection and can construct a replay stream URL.

## Delivered requirements and specifications

### Subscription and live forwarding

- `GET /api/v1/reports/replay` requires `race:read`. It accepts `eventId`,
  optional `sessionId`, `mode` (`live` or `replay`), `speed`, and an optional
  `streamId`. Invalid mode/speed and missing event/session selections are
  rejected; a missing stream ID is generated by the server.
- The server loads records for the selected event and optional session from
  Event Catalog race state. The hub filters records to that selection and sorts
  them by timestamp and record sequence.
- Replay emits a `replay-ready` message, `replay-snapshot` with previously
  emitted records and state, then `replay-state`. It emits each record as
  `race-record`, preserving the recorded interval scaled by replay speed.
- A subscriber reconnecting to a known replay stream ID receives its current
  emitted-record snapshot and state. A stream ID cannot be reused for a
  different event/session selection.
- Live mode sends `replay-ready` and an empty `replay-snapshot`, then forwards
  only newly published matching records as `race-record`.

### Controls and lifecycle

- `POST /api/v1/reports/replay/control` requires `race:write`. It accepts a
  known stream ID and `start`, `pause`, `resume`, `reset`, or `set-speed`.
  Any authorized writer can control the stream; there is no creator-only lock.
- Replay speed is finite and between 0.01 and 1000. Pause stops its timer;
  resume schedules the next record; start and reset restart from zero;
  speed changes reschedule playback. The endpoint returns the resulting state.
- Reset and start broadcast `replay-reset`; controls broadcast `replay-state`.
  Completion broadcasts `replay-complete` and closes subscribers. Server
  shutdown clears replay timers, live subscriptions, and replay subscribers.
- Timer delays are clamped to the JavaScript maximum. SSE heartbeat comments
  keep open subscriptions active.

### Reports controls and documentation

- Reports offers event/session selection, live/replay mode, speed choices,
  start/pause/resume/reset, and a new-stream action. It shows the authenticated
  SSE URL and the result or error from a control request.
- OpenAPI documents the existing replay subscription and control routes.
  These route descriptions reflect the current foundation, not the protocol
  contract planned in spec 08.

## Resolved questions and scope boundary

- SSE is the subscription transport and HTTP is the control transport.
- A named stream belongs to one event/session selection. Late subscribers can
  observe its current snapshot without starting a second replay.
- The current event names and payloads are implementation details of this
  foundation. Spec 08 replaces them with the stable typed protocol; clients
  and OpenAPI must be updated together.
- The Reports control panel currently exposes a stream URL; it does not
  subscribe to and render the replay state or records itself.

## Failure handling

- Reject unknown events/sessions, invalid modes/speeds, missing control
  streams, and stream IDs reused for another selection.
- Pause clears the replay timer. Subscriber disposal clears that response's
  heartbeat and detaches it while the named replay remains available for
  reconnection. Completion closes subscribers; shutdown clears all timers.
- An authorization failure must not open a subscription or issue a control.

## Verification and regression tests

- Hub tests cover timestamp ordering, interval speed scaling, matching live
  records, late-subscriber snapshots, pause/resume, completion, and cleanup.
- Server tests cover authenticated event/session replay, a control request,
  missing stream and event errors. Reports UI integration tests cover event/
  session selection, mode and speed controls, and generated stream URLs.
- Future protocol work must retain these foundations while adding the event
  and seek contract tests in spec 08.
